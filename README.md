# Sreemantha Hospital Platform

Full-stack website and clinical CMS for Sreemantha Hospital (Khammam).

- **Backend:** Node.js 20 + Express 5 + MySQL (`mysql2`)
- **Frontend:** React 19 + TypeScript + Vite + Tailwind CSS 4
- **Deployment target:** GoDaddy Node.js Hosting (single Node process serves the API and the built SPA)

## Project structure

```
.
├── package.json          # GoDaddy entry point: build/start/dev scripts + workspaces
├── .npmrc                # public npm registry (required by GoDaddy hosting)
├── backend/
│   ├── src/              # Express app, routes, controllers, DB bootstrap
│   ├── uploads/          # committed baseline media + runtime uploads
│   └── database_godaddy_export.sql
└── frontend/
    ├── src/              # React SPA and admin CMS
    └── dist/             # generated by `npm run build` (not committed)
```

## Requirements

- Node.js **20.x** (the version configured for GoDaddy Node.js Hosting)
- npm 10+
- A MySQL 8 database (GoDaddy provides one when attached to the hosting app)

## Local development

```bash
# 1. Install all workspace dependencies from the repo root
npm install

# 2. Configure local environment
cp backend/.env.example backend/.env
# edit backend/.env and set DB_* / JWT_SECRET

# 3. Build the SPA and start the full-stack server
npm run build
npm start
# open http://localhost:5000
```

Useful scripts:

| Script | Purpose |
| --- | --- |
| `npm run dev` | Builds the SPA, then starts the backend on `PORT` (used by GoDaddy preview) |
| `npm run dev:backend` | Starts only the Express API (port 5000) |
| `npm run dev:frontend` | Starts the Vite dev server (port 5173, proxies `/api` and `/uploads`) |
| `npm run build` | Builds the production SPA into `frontend/dist` |
| `npm start` | Starts the production server (serves API + SPA) |
| `npm run test:backend` | Runs the Node test suite |
| `npm run test:e2e` | Runs Playwright end-to-end tests |
| `npm run validate:deploy` | Verifies the GoDaddy Node.js Hosting contract locally |

## Environment variables

GoDaddy injects the database variables automatically when the hosted database is attached. Do not hard-code them.

| Variable | Required | Description |
| --- | --- | --- |
| `PORT` | Set by platform | HTTP port. The app falls back to `5000` locally. |
| `NODE_ENV` | Recommended | Set to `production` on GoDaddy. |
| `DB_HOST` | Yes (injected) | MySQL host. |
| `DB_PORT` | Yes (injected) | MySQL port. |
| `DB_NAME` | Yes (injected) | MySQL database name. |
| `DB_USER` | Yes (injected) | MySQL user. |
| `DB_PASSWORD` | Yes (injected) | MySQL password. |
| `DB_SSL` | Optional | Set `true` only if the database requires TLS. |
| `JWT_SECRET` | Strongly recommended | Long random signing secret. If omitted, the app generates and persists `backend/data/.jwt-secret`. |
| `JWT_EXPIRES_IN` | Optional | Token lifetime (default `7d`). |
| `UPLOAD_DIR` | Optional | Absolute path for persisted uploads. Defaults to `backend/uploads`. |
| `SEED_SUPERADMIN_PASSWORD` | Optional | Initial password used only when the superadmin account does not exist. |
| `SEED_ADMIN_PASSWORD` | Optional | Initial password used only when the admin account does not exist. |
| `SEED_STAFF_PASSWORD` | Optional | Initial password used only when the staff account does not exist. |
| `LOG_LEVEL` | Optional | `error`, `warn`, `info`, `http`, or `debug`. |

## GoDaddy Node.js Hosting

The repository root is the deployable app. GoDaddy runs:

1. **Production install** (`npm install`, `devDependencies` omitted)
2. **`npm run build`**
3. **`npm start`** (published environment) or **`npm run dev`** (preview)

The root `package.json` therefore contains:

```json
{
  "main": "backend/src/server.js",
  "engines": { "node": "20.x" },
  "scripts": {
    "build": "npm run build:frontend",
    "start": "node backend/src/server.js",
    "dev": "node backend/src/server.js"
  }
}
```

`backend` and `frontend` are npm workspaces, so the single production install at the repository root installs every runtime and build dependency. The server binds to `process.env.PORT` on `0.0.0.0` and serves both `/api/*` and the built SPA from `frontend/dist`.

### Before you publish

- [ ] Attach the hosted MySQL database; confirm `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, and `DB_PASSWORD` are present in the Secrets card.
- [ ] Add a `JWT_SECRET` secret (long random value).
- [ ] Set `NODE_ENV=production`.
- [ ] Do not upload `node_modules`, `.env`, `frontend/dist`, or `test-results` (all are gitignored).
- [ ] Deploy the repository root (GoDaddy Git sync or zip).
- [ ] After first boot, sign in and change the default account passwords.

### Database bootstrap

On boot the app verifies/creates all tables, applies backwards-compatible schema upgrades, and seeds baseline content only into empty tables. Existing users and content are never overwritten. `backend/database_godaddy_export.sql` is available for manual imports if you prefer to seed the hosted database from SQL.

### Media persistence

Committed media under `backend/uploads` ships with the code. Files uploaded through the CMS are written to `UPLOAD_DIR` (default `backend/uploads`) and served from `/uploads`. If the hosting filesystem is replaced on each deploy, point `UPLOAD_DIR` at a persistent path or volume and migrate the existing files there.

## Security notes

- Passwords are hashed with Argon2id; bcrypt legacy hashes are upgraded on successful login.
- There is no hard-coded JWT signing key. Set `JWT_SECRET` in production for sessions that survive restarts and redeploys.
- The initial seed accounts are created only when missing. Change their passwords immediately after the first login.
- API responses containing user records never substitute a known default password for a missing stored credential.
- Sign-in and public appointment/enquiry endpoints use in-memory rate limits to blunt credential stuffing and form spam. The counters reset when the process restarts; GoDaddy runs this app as a single Node process.
- The CMS credential-recovery view stores the last password set by an administrator in `users.stored_password` so authorized administrators can hand credentials to staff. Treat database access as sensitive and use a dedicated MySQL user for the application.
